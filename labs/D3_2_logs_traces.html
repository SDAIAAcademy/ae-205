Goal

Make every log line of Farz a JSON record that carries the request id and no personal data, prove it with a test, and follow the slowest request of a replay through its spans to the step that made it slow.

What you need

  • The lab folder rifd-labs/3.2: a service that logs the whole claim, a logger without its redaction step, and no span around the policy lookup
  • structlog for the logs and the OpenTelemetry SDK for the spans; the spans go to runs/spans.jsonl, so no collector is needed
  • AI policy: tutor.

Find the personal fields in the current logs 4 min

cd rifd-labs/3.2
RIFD_LOG_FILE=runs/service.log RIFD_TRACE_FILE=runs/spans.jsonl uv run uvicorn rifd.app:app --port 8000 &
uv run python tools/replay.py --file ../data/replay/week1.csv --rate 40 --limit 200 --out runs/replay.jsonl
grep -c national_id runs/service.log

Stop the server and delete runs/service.log and runs/spans.jsonl before the next run.

Log JSON with a request id; redact at the edge 9 min

In src/rifd/app.py, log the claim id, line, label and version instead of the whole claim. In src/rifd/logs.py, bind the request id in bind_request() and put the redact processor back in the chain, as a last defence if someone logs a member field again. Run uv run pytest tests/test_redaction.py.

Add spans; find the slowest request and its slow span 8 min

In app.py, wrap the policy lookup in tr.start_as_current_span("policy_lookup"). Run the replay again with 400 claims, then find the slowest request (the span with no parent and the longest duration) and its children.

uv run python -c "import json; s=[json.loads(x) for x in open('runs/spans.jsonl')]; r=max((x for x in s if not x['parent_id']), key=lambda x: x['duration_ms']); print(r['duration_ms'], [(x['name'], x['duration_ms']) for x in s if x['trace_id']==r['trace_id']])"

Write runs/slowest.md: the trace, its spans with their times, and which step made it slow.

For the trainer

In the course's run the start state wrote 200 of its 401 log lines with a national id or a mobile number: every triage line, because it logged the claim with its member block. After the fix none did, every request line carried a request id, and 7.0% of 401 requests called the policy lookup. The slowest request's trace was POST /v1/triage with policy_lookup taking nearly all of its time and predict about 2 ms. The lookup is a 120 ms wait; on the shared laptop of the course's run it stretched to several hundred milliseconds, so expect smaller numbers on a quiet machine.

Answers: in a trace attribute, an exception message that prints the body, the access log of a proxy; the main defence is not logging the body at all, because a pattern cannot know every way personal data is written; about 7%, which is more than the 5% the 95th percentile ignores, so the 95th percentile falls inside the slow requests. Solution: labs/solutions/S3_2.py.
