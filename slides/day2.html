An image

An image is a stack of read-only layers and a few settings

  • Each RUN, COPY and ADD line adds a layer: the files it changed
  • ENV, USER, CMD and EXPOSE only change the configuration, which anyone who pulls the image can read
  • A container is the image plus one thin writable layer that disappears with it

In the case study

One image, rifd/claims:1.0.0, serves both Farz and Shabih; RIFD_SERVICE picks which one starts.

The Open Container Initiative image specification defines this: an image is a manifest, a configuration and an ordered list of layers. Ask: if a later layer deletes a file an earlier layer added, is the file gone from the image? No, it is hidden but still shipped. That matters for secrets in session 2.

The build cache

Change a file, and every layer after the line that copied it is rebuilt

FROM python:3.12
WORKDIR /app
COPY . .
RUN pip install uv && uv sync
COPY pyproject.toml uv.lock ./
RUN uv sync --frozen --no-dev --no-install-project
COPY src ./src
RUN uv sync --frozen --no-dev
Order by how often things change. The lock changes rarely, the code often: copy the lock first and the dependency layer stays cached.

On the left, any edit to any file in the folder invalidates COPY . ., so every build reinstalls every dependency. On the right, a code change rebuilds only the last two lines. The --no-install-project pattern is from uv's Docker guide. Ask the room to predict what a change to uv.lock rebuilds on the right: everything from the second line.

Multi-stage builds

Build in one stage, ship only the result from a second

Stage 1 · buildslim base, uv, the lock, uv sync --frozen --no-dev
→
COPY --from=build.venv, src; then models/
→
Stage 2 · runtimea fresh slim base, user 10001, no uv, no caches
Takeaway. Whatever the build needed and the service does not stays in stage 1 and never ships.

Press once per step. The runtime stage starts from the same base so that the virtual environment's interpreter path still works. --frozen installs exactly what the lock says without solving again or checking it against pyproject.toml (--locked would also fail when the lock is out of date); --no-dev leaves out pytest, Locust and pip-audit.

Two small lines

A slim base and a non-root user cost nothing and remove a lot

python:3.12-slim

Debian with the minimum Python needs. The full python:3.12 image adds compilers and headers, which a service that installs wheels does not use and a scanner still reports.

USER 10001

A process that escapes the service holds no root rights in the container. The cluster can enforce it with runAsNonRoot in the manifest.

What goes wrong. A tag like python:3 or latest moves under you: pin the tag, or the digest when two builds must be identical.

The verified images of the course's run are python:3.12-slim and ghcr.io/astral-sh/uv:0.13.5. Distroless or Alpine bases are smaller still; Alpine uses musl, so some wheels must be built from source. For this course, slim is the default and the stretch asks for a digest pin.

Vulnerability scanning

A scanner matches what is installed against lists of known flaws

It reads

  • the system packages of the base image
  • the language packages: a lock file, or the installed environment

It compares with

  • advisory databases such as OSV and the GitHub advisories
  • each advisory names affected versions and the version that fixes it
A scan is a date. The same image scanned next month can report more: new advisories are published every day.

Trivy and Grype scan images, both system and language packages; pip-audit scans Python dependencies from a requirements file or an environment. The lab uses pip-audit, which runs without a container runtime, and the trainer may show Trivy on the image. A scanner finds known flaws in packages; it does not find bugs in Rifd's own code.

Secrets

A key in an ENV line is readable by anyone who can pull the image

ENV RIFD_LOOKUP_KEY=rifd-lookup-key-for-the-labs-only \
    RIFD_MODEL_DIR=/app/models/farz-1.0.0
  • docker history --no-trunc and docker inspect print it
  • Deleting it in a later layer hides it, does not remove it
  • Every pushed copy keeps it: rotate the key, then fix the file
Supply it at run time. An environment variable from the runtime, a mounted file, or a cluster Secret; a key the build needs goes through BuildKit's --mount=type=secret.

The key in the lab is a fake made for the labs. The lab's check also searches every text file of the project for it, because the code had it too, in settings.py. Ask: who could pull the supplied image last quarter? Everyone with access to the registry, and every laptop that ever pulled it.

Configuration

The service reads its settings; the runtime decides them

def _secret(name: str) -> str:
    """A secret comes from the environment, or from a file the runtime mounts."""
    if os.environ.get(name):
        return os.environ[name]
    path = Path(os.environ.get(name + "_FILE", "secrets/lookup.key"))
    return path.read_text(encoding="utf-8").strip() if path.is_file() else ""

lookup_key: str = field(default_factory=lambda: _secret("RIFD_LOOKUP_KEY"))
  • Same image in every environment; only the configuration differs
  • secrets/ is in .gitignore and .dockerignore

From the course's settings.py, with the docstring shortened. This is the twelve-factor rule "store config in the environment", with a file as a second source because a cluster mounts Secrets as files as well as variables. The check sets the variable and confirms the service reads it.

A cluster in four objects

You describe what should run; the cluster keeps it running

Deployment

How many copies of which image, with which settings; it replaces pods that die.

Pod

One running copy: a container with its probes and limits.

Service

One stable address in front of the ready pods that match its selector.

ConfigMap and Secret

Settings, and keys, given to the pods as variables or files.

The lab uses kind, which runs a whole cluster inside one container; k3d and minikube work the same for this lab. Ask: the Service sends traffic to which pods? Only those whose readiness probe passes: that is where Day 1's /readyz pays off.

Probes

Three probes, three different actions

ProbeFarz asksWhen it fails, the cluster
startupProbe/readyz every 2 s, up to 30 timesrestarts the container after a minute; holds the other probes until it passes
readinessProbe/readyz every 5 stakes the pod out of the Service; does not restart it
livenessProbe/livez every 10 srestarts the container
A slow start is not a dead process. The startup probe gives the model time to load without loosening the liveness probe.

Values are those of the course's k8s/farz.yaml. Farz took 11 to 22 seconds from process start to ready on the course's laptop runs, mostly Python imports, which is why a minute of startup budget is safe. Ask: what would happen with a liveness probe on /readyz and no startup probe? A pod that loads slowly is killed before it is ever ready.

Requests and limits

Requests place the pod; limits stop it from taking the node

resources:
  requests: {cpu: 250m, memory: 256Mi}
  limits:   {cpu: "1", memory: 512Mi}
  • The scheduler places a pod on a node with room for its requests
  • Over its CPU limit, a container is slowed down
  • Over its memory limit, it is killed (OOMKilled) and restarted
What goes wrong. No limits: one pod with a leak takes the node and its neighbours with it. Limits far below use: a restart loop under load.

Farz measured 184 MiB at ready in the course's run (lab 2.4 measures it), so 256Mi requested and 512Mi as a limit leave room. Day 3's sizing decides the CPU numbers from a load test rather than a guess.

Where may it run?

The data each service holds decides where it may run

  • The national Data Classification Policy has four levels: Top Secret, Secret, Restricted, Public
  • Claims with names, national ids and health details: Rifd classifies them Restricted and keeps them on its in-Kingdom cluster
  • A copy abroad is a transfer under the Personal Data Protection Law and its transfer regulation

The lab's table

Farz, Shabih and the dashboards: what each holds, its level, where it may run, and who signs. Bassam Al-Jaber signs with Munira Al-Ajmi.

The four levels are those of the national policy; that Rifd keeps Restricted data in the Kingdom is Rifd's own rule in the case study, not a quotation of the law. The dashboards are the interesting row: aggregate counts with no claim content can be classified lower, by a written decision, if the Day 3 redaction tests prove that nothing personal reaches them. Sources: Data Classification Policy; PDPL and the Regulation on Personal Data Transfer outside the Kingdom (SDAIA).

The second model

Shabih turns a description into 96 numbers and finds the nearest past claims

Description"Windscreen cracked by a stone on the highway"
→
Encodercharacter n-grams, then 96 dimensions, unit length
→
Index50,000 vectors in memory; dot product with each
→
Answerthe k nearest: claim id, line, incident, score

Kholoud Al-Ghannam, a senior adjuster, uses Shabih to see how similar claims were settled. The encoder is a TF-IDF on character n-grams reduced by SVD, trained on the synthetic descriptions; it needs no model download and runs on any laptop. A pretrained sentence encoder would give better neighbours and the serving questions would be the same: memory, start-up, and what the answer may contain.

What it costs

The index lives in memory, and loading it is the slow part

19 MB
50,000 × 96 float32 numbers
586 ms
Shabih's model load, against 60 ms for Farz
+40 MiB
memory at ready, 223 against 184 MiB

Searching every vector is fine at this size. Beyond a few million, an approximate index (HNSW, IVF) trades a little recall for much less time.

Measured in the course's run of lab 2.4 on a laptop. Time to ready was 18.7 s for Shabih and 21.9 s for Farz: mostly imports, and it varies from run to run, so read the load times for the difference between the models. The index size is arithmetic: 50,000 × 96 × 4 bytes.

The contract

/v1/similar returns claims, not people

{"description": "Windscreen cracked by a stone",
 "line": "motor", "k": 3}
{"results": [
  {"claim_id": "CLM-…", "line": "motor",
   "incident": "windscreen", "score": 0.9}, …],
 "model": {"name": "shabih", "version": "1.0.0"}}
Minimise at the source. The index keeps claim id, line and incident type only: no name, national id or description can leak through an answer it does not hold.

The example scores are illustrative; the tests check the shape and that no personal field appears. Same rules as Farz: unknown fields refused, k between 1 and 20, typed errors. Ask: an adjuster wants the description of each neighbour. Where should that come from? The claims system, with its own access control, by claim id.
