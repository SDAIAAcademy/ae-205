An artefact

Four files, each the answer to a question someone will ask

model.skops

What computes the probabilities? Saved so that loading runs no code.

signature.json

What goes in and comes out? Ten input fields with types, three labels out.

metadata.json

Which version, which data, which decision rule, which sha256, which ten reference predictions?

requirements.txt

Which exact library versions load it? Six lines with ==.

MLflow's model format has the same parts under other names: the model files, a signature, an input example and a requirements file. Ask: which file would the serving team read first? The signature: it is the contract between the model and the API they will write in session 3.

Why a registry

A registry answers "which model gave this answer?" in one lookup

  • An adjuster disputes a triage: which version scored that claim, trained on which data?
  • A canary misbehaves: what exactly changed between the two versions?
  • An auditor asks for the model that ran in March: can you load it today?
  • Two teams both say "the new model": are they talking about the same file?
What goes wrong. A folder called final_v2_really on a shared drive answers none of these.

Each question is one Rifd will meet in the next four days: the dispute in Day 3's logs, the canary on Day 4, the audit in the runbook. Ask which of them the room can answer today for a model they own.

Aliases

An alias moves; a version does not

farz@champion → 1.0.0

Moving the alias changes what every reader of the alias loads, with no deployment.

farz 1.0.0

Always the same file. A rollback is a change of one line in the manifest, and the manifest says what runs.

Rifd's rule. Production names a version; staging and the weekly batch may follow champion.

This is a design choice, and Rifd's rule is one reasonable answer. The other answer, production following an alias, makes releases fast and audits hard: the manifest no longer says which model ran. MLflow writes an alias as models:/farz@champion.

Contract first

Write the contract before the code, and test the code against it

| amount_sar        | number  | over 0, up to 5,000,000 |
| vehicle_age_years | integer | 0 to 60; motor: needed  |
| in_network        | boolean | health: needed          |
| member            | object  | never sent to the model,
                                never logged            |
  • Agreed with the claims system's team: they build against it while you build the service
  • Every rule becomes a test in tests/test_contract.py
  • A change that breaks a caller is a new major version of the path

The full contract is in each lab folder as CONTRACT.md. Point out the member line: personal data arrives with the claim because the claims system sends whole records; the contract says what happens to it. That is a decision Bassam, the data protection officer, signed.

Input validation

Every field is checked before the model sees it

class Claim(BaseModel):
    model_config = ConfigDict(extra="forbid")
    line: Literal["motor", "health", "property"]
    amount_sar: float = Field(gt=0, le=5_000_000)
    vehicle_age_years: int | None = Field(default=None, ge=0, le=60)

    @model_validator(mode="after")
    def by_line(self):
        if self.line == "motor" and self.vehicle_age_years is None:
            raise ValueError("a motor claim needs vehicle_age_years")
        return self

A model given a negative amount or an unknown line still returns a probability: models do not refuse bad input, so the service must. extra="forbid" refuses a field the contract does not know, because a caller who sends it believes it has an effect. The rule across fields is a model validator that raises ValueError, which FastAPI turns into a validation error.

Typed errors

A caller switches on the error's type, never on its text

typestatusThe caller
validation-error422fixes the claim; never retries it as it is
model-unavailable503retries later, or sends the claim to manual triage
dependency-failed502retries later
prediction-failed500reports the request id
What goes wrong. A 200 with "error": "bad input" in the body: every dashboard counts it as a success.

The types are URNs (urn:rifd:problem:validation-error) so that they cannot be mistaken for a web page. The warning matters on Day 3: an error hidden in a 200 is invisible to the error-rate metric and to the alert.

Problem details

One shape for every error: RFC 9457

{
  "type": "urn:rifd:problem:validation-error",
  "title": "The claim does not match the contract",
  "status": 422,
  "detail": "1 field(s) failed validation",
  "instance": "/v1/triage",
  "errors": [{"field": "line", "message": "Input should be 'motor', 'health' or 'property'"}],
  "request_id": "3f1c9a0d7e2b4c55"
}

RFC 9457, Problem Details for HTTP APIs, defines type, title, status, detail and instance and allows extra members such as errors. The request id lets the caller and the on-call engineer find the same request in the logs on Day 3. Sources: RFC 9457.

Versions in two places

The path carries the contract's version; the body carries the model's

/v1/triage

Changes only when the contract breaks a caller. /v2/ runs beside /v1/ until every caller has moved.

"model": {"version": "1.1.0"}

Changes with every release, contract unchanged. The first hop of lineage, and the field Day 4's canary comparison groups by.

Ask: a new model needs one extra input field. Is that /v2? Only if callers must send it; an optional field with a default keeps /v1. Keep the two version numbers apart: mixing them forces a contract change for every retraining.

Health and readiness

"Is it alive?" and "should it get traffic?" are two questions

/livez · liveness

Can the process answer at all? If not, restart it. Never looks at the model or at a dependency.

/readyz · readiness

Is the model loaded, verified and warm? If not, send no traffic here, and do not restart.

What goes wrong. One /health that says OK: traffic reaches a pod with no model, and every claim fails.

Kubernetes acts on the two answers differently: a failed liveness probe restarts the container; a failed readiness probe removes the pod from the service's endpoints. Day 2 wires both into the manifest. Sources: Kubernetes documentation, liveness, readiness and startup probes.

What each failure means

A wrong check turns a bad file into a restart loop

The last row is the trap. A pod restarted forever hides the reason in a crash count; a pod that is alive and not ready says "no artefact at models/farz-1.0.0" at /readyz, where the on-call engineer can read it.

Lab 1.4 · step 2

Load and warm in the lifespan, before the first request

@asynccontextmanager
async def lifespan(app: FastAPI):
    logs.configure(s.log_file)
    load_farz(app)        # load, verify sha256, warm up; never raises
    yield

def load_farz(app):
    try:
        model = artefact.load(s.model_dir)
        warm = model.predict([model.meta["reference"][0]["input"]])
        ...
        app.state.ready = True
    except Exception as e:
        app.state.load_error = str(e)   # alive, not ready, and says why

The important line is the last: a failed load does not crash the process. The process stays alive, /readyz reports the reason, and the cluster keeps traffic away. Crashing would also work for the cluster, but the reason would be lost in a restart count.
